# SG-P22 — PDF Welcome Book technical feasibility gate

Research date: **2026-11-12**, Europe/Athens. **Feasibility research only; implementation has not started.** No dependency, font, provider or architectural choice is approved by this proposal. D-013 remains open in [DECISIONS.md](DECISIONS.md). Scope follows [IMPLEMENTATION_TASKS.md](IMPLEMENTATION_TASKS.md), [PRODUCT_SPEC.md](PRODUCT_SPEC.md), [DESIGN_SYSTEM.md](DESIGN_SYSTEM.md), [SECURITY.md](SECURITY.md) and [TESTING.md](TESTING.md).

## Recommendation and approval gate

**Primary recommendation:** generate an independent PDF **on demand in the owner-authorized host browser**, using a locally served, version-pinned **pdfmake browser build** with explicitly approved embedded fonts. Load the library/fonts only when the host requests an export. Use declarative text flow, not screenshots of guest HTML. A4/A5 book layout consumes an immutable snapshot of the same saved property content used by the guide; no separate editor, generation service, public PDF endpoint or persistent PDF storage.

**One fallback:** an owner-approved, host-side printable HTML book using native **Print / Save as PDF**, built from the same content projection. This offers a useful manual route if direct generation fails, but print dialogs/settings/output vary. It **does not independently satisfy** the one-click downloadable-PDF requirement, and does not count as completing SG-P22 by itself. The existing SG-P21 A5 QR card is preserved and is not a multipage-book fallback already implemented.

Why: pdfmake provides a documented flow/layout layer and break controls instead of requiring a bespoke paginator. Browser generation avoids recurring PDF-specific server compute, server rendering abuse and a new data processor. Its costs are nontrivial host-side code/font transfer, parsing, CPU and memory. This is a conditional engineering recommendation, **not verified output or compatibility in StayGuide**. Exact approved artifacts, bundle budget, Greek/shaping/glyph coverage, worst-case page flow and real mobile downloads must pass the bounded post-approval checks below before shipping. If they fail, return to the owner rather than switch dependencies or buy a service silently.

- `/g/:id/card` is a single public HTML welcome card. `public/print.css` specifies A5; `print.js` calls browser printing. Existing `tests/qr-print.browser.mjs` inspects Chrome-generated A5 PDFs, normal/long property names and text extraction. Those historical checks do not establish a multipage A4/A5 book, Greek font coverage, other-browser output or physical scanning/printing.
- `node/server.mjs` is a local adapter with persisted JSON; its assets MIME map lacks font/PDF entries. Cloudflare uses `wrangler.jsonc`: Worker + static assets, D1 placeholder, `compatibility_date: 2026-11-10`, selective Worker-first `/api/*` and `/g/*`. No headless browser binding, PDF library or font assets exist. There is no framework/build pipeline for the frontend.
- Current temporary owner tokens remain browser-local; public noindex is not confidentiality. Arbitrary free text has no reliable semantic separation between guest information and secrets. This is a real export-policy risk, not solved by a library or a field allowlist.

### Cross-cutting capability assessment

- **Readable A4/A5 prose:** use flowing single-column text. Keep headings with initial body lines, let long body blocks span pages and avoid wrapping an entire section in an unbreakable container. Preserve paragraph/newline intent; avoid over-aggressive line normalization. Decide/test long URLs and unbroken 2,000-character tokens explicitly. Do not shrink type to make content fit a fixed number of pages.
- **Unicode is more than UTF-8 acceptance:** embedding a font with Greek glyphs is necessary, not sufficient for all scripts. Test accents, decomposed combining marks, Greek tonos/polytonic, Cyrillic, bidirectional Arabic/Hebrew, CJK and emoji separately. One Latin/Greek/Cyrillic font cannot promise universal glyph coverage or complex-script layout. Unsupported characters must be detected and surfaced; never silently drop/replace text. Owner must approve additional font/script support or an explicit limitation before release; native print is a disclosed partial fallback, not a Unicode-certification shortcut.
- **Fonts/licensing/size:** propose local static TTF Regular/Bold from a pinned Noto Sans artifact with proven Greek/required-script coverage (S26/S27), not the entire Noto collection or a runtime Google Fonts request. Exact files still need selection/license/coverage review and layout-engine tests; variable-font support must not be assumed. Retain library/transitive/font notices. VFS base64 increases transferred uncompressed font bytes roughly 4/3; subsetting can reduce embedded output but needs glyph/shaping/license tests. Initial priority is correct coverage over aggressive subsetting. Separate style-specific font assets matter even when body text looks similar.
- **PDF file size:** fonts and later images can dominate text. Embed only used approved faces and verify actual subsetting/compression behavior; don't claim small file sizes without measuring exports. Lazy loading removes these bytes from guest/marketing and normal dashboard startup, but does not eliminate first-export transfer/parse cost. Cache immutable versioned library/font assets, not guide content/PDFs.
- **QR:** reuse the exact canonical SVG fetched through the existing same-origin `/g/:id/qr.svg` route, without owner-token headers; validate response/type/size and selected property. pdfmake SVG embedding is documented (S04), but SVG-to-PDFKit conversion must preserve geometry/quiet zone/white backdrop in tests. Don't use its independent QR encoder simply because one exists. If canonical SVG conversion fails, stop for review rather than silently change encoder or destination. Existing high-resolution canonical PNG is another representation to investigate only if needed, not a new primary architecture.
- **Future images:** pdfmake/PDFKit and the other candidates have image paths, but that does not implement SG-P30. Later use only validated optimized same-origin bytes, explicit dimensions, captions/alt-equivalent descriptions, bounded decoded pixels and tested page fit. No remote URL fetch from arbitrary saved strings, no image upload/storage prerequisite for this text-only book.
- **Consistency/accessibility:** embedded fixed fonts and layout code should improve page consistency across devices, but byte differences/metadata and download behavior are separate. Keep text selectable/searchable and logical reading order; do not claim tagged PDF/PDF-UA support from appearance or extraction alone. Native guest HTML remains the accessible reading alternative; evaluate PDF reading order/assistive technology explicitly.

## Economics: assumptions, formulas and scale

All USD rates below are observed provider documentation **as of 2026-11-12**, excluding tax/other services; the product target is provisional **€1/property/year**, not an exchange-rate or viability calculation. No customer export rate, latency, CPU or conversion measurement exists. Examples are sensitivity scenarios chosen for arithmetic, not forecasts. Existing guide GET/D1/hosting/translation/support/payment costs remain separate.

### Primary browser architecture

`N = P × E`: properties times exports per period. Browser generation adds **no server PDF-rendering invocation or PDF-object storage per export**; the work happens on the host device. It may add a fresh owner-authorized guide read and canonical QR read, plus library/font asset downloads on a cold asset cache. Repeated exports on a warm asset cache still consume browser CPU/memory but need not repeatedly transfer the library/fonts. Do not claim a warm cache eliminates the need to read current saved content.

| Explicit hypothetical workload | Browser generation implications | Cost certainty / unknowns |
|---|---|---|
| One property, one occasional export | One generation; cold assets only if needed; existing content/QR requests | No PDF service fee. Actual payload/client time and existing backend charges unmeasured. |
| One host exporting 20 times after edits | 20 generations of current snapshots; cache code/fonts, not old PDFs | No 20-fold PDF hosting/storage charge; client work scales with exports. Asset caches may miss. |
| 10,000 properties, 12 exports each/year | 120,000 generations/year distributed over host devices; cold loads depend on devices/cache retention, not just property count | No centralized PDF compute fleet required. This is not an observed usage rate; backend reads, client performance and hosting plans still need verification. |

S22 documents static-asset requests as free/unlimited on Workers Static Assets; do not generalize that to DB reads, Worker-cached dynamic responses or all hosting providers. If code/fonts are served through a dynamic wrapper, its invocation may be billable. No provider/plan is selected by this calculation.

### Ordinary Worker alternative sensitivity

S22: Workers Free 100,000 requests/day and 10 ms CPU/invocation; Paid subscription $5/month, includes 10 million requests and 30 million CPU-ms/month; overages $0.30/million requests and $0.02/million CPU-ms. Paid CPU can be configured higher, but the 128 MB isolate limit and startup/dependency costs remain (S21).

Let `N` be monthly PDF requests, `c` the measured mean CPU-ms/request **including font/layout costs**, and `R`, `M` the plan allowances still available after other app traffic. An illustrative incremental overage calculation is:

`$0.30 × max(0, N − R)/1,000,000 + $0.02 × max(0, N×c − M)/1,000,000`.

Add the $5/month base **if adopting Paid solely for this feature**, plus separately priced services and safety controls. Do not attribute shared plan allowances twice. Occasional or 20-export use substitutes `N=1` or `20`; costs depend on `c` and remaining allowances, not a promised free quota. The 120,000/year scenario is not a monthly burst assumption; distribution matters.

For a scale sensitivity only, assume all allowances already consumed: 120,000 exports/year and an **unmeasured illustrative** `c=100 ms` imply $0.036 request overages + $0.24 CPU = $0.276/year; `c=1,000 ms` instead yields $2.436/year. These are arithmetic examples **not benchmarks, bills or runtime feasibility proof**, exclude the potential $60/year plan base, DB/storage and other costs, and cannot justify relying on the Free CPU limit. Server compute may be cheap; compatibility, abuse and maintenance are the stronger reasons not to start there.

### Managed-browser alternative

S24: Free browser-time allowance 10 minutes/day; Paid includes 10 hours/month then $0.09/additional hour. Browser Sessions also have a concurrency allowance (10 on Paid), then $2 per additional browser under the documented monthly-average peak calculation; Quick Actions are charged for browser time only. These are distinct from Worker request/CPU charges and plan base.

Let `s` be observed billable browser seconds/export and `H` remaining included browser hours. A rough pre-rounding time component is `$0.09 × max(0, N×s/3600 − H)`; final billing follows the provider's monthly rounding rules, with any session-concurrency cost separate. No `s` was measured, so no per-export price or end-to-end latency is claimed. Don't interpret an allowance as an SLA or exemption from account/rate limits. At €1/year, even inexpensive rendering should not introduce an unneeded service, processor or operational obligation; it could be reconsidered with measured need and approval.

### Download, cache or persist?

Prefer **generate when requested → download directly as a Blob → release it**. Do not generate on save/guest view or keep PDFs in localStorage, a service-worker cache, shared HTTP cache, D1 or R2. Browser memory can hold the one current attempt; discard on property/source-version change and revoke object URLs after safe use. Re-export after edits instead of serving an old document.

Persistent PDFs add invalidation/versioning, account authorization, sensitive Wi-Fi retention, deletion/export responsibilities, storage operations and potentially stale QR/domain references. They are not needed for first filled-book use. If later measured repeat costs justify caching, key by content revision, format, font/template version and access policy, with explicit retention/deletion decisions. That is separate scope. Native print similarly uses local device work, but still has asset/content fetch costs and user interaction.

## Recommended content and workspace architecture

### Single saved-content projection

Propose a small shared pure **section definition/content projection**, not scraping the guest DOM and not duplicating data entry. Inputs: an explicitly captured property identity, validated saved model and exact guest URL. Output: ordered, nonempty text blocks with stable existing IDs/labels and optional approved sublabels (Wi-Fi, check-in/out). No tokens, DB row/metadata, arbitrary object spreading, hidden form fields or unsaved drafts. Separate cover property name from optional welcome text. Preserve existing required-field/length/whitespace semantics.

The current host and guest differ in order. Proposed book order: cover → welcome → Wi-Fi → arrival/departure → rules → appliances → parking/transport → local favourites → emergency → contact → additional; omit empty content. A later prompt must approve extracting/reusing definitions and regression-prove unchanged existing host/guest order and DOM contracts. Use renderer-specific order arrays over the same stable definitions if necessary; don't redesign guest pages just to share code.

The projection is the shared business rule; pdfmake nodes and native HTML are small presentation adapters. Share only semantic values/order/filtering, not a second editor or two divergent eligibility/validation implementations. Don't prematurely build a generic template framework. Translation/photo/optional-section/book-blank variants remain outside this task and must not alter the first model or make a new schema/API prerequisite.

### Minimal host interaction and output design

In the existing SG-P21 workspace, after implementation approval add one modest **Welcome Book PDF** group with an A4/A5 portrait choice and Download action. Keep existing QR downloads and single-card preview intact. No empty book/print-kit/theme navigation. A clean new-property book may contain its named cover plus correct QR and concise empty-content indication; never invent instructions, demand extra onboarding or substitute a blank writing template. Owner should review that minimal-content policy.

Use a restrained violet/ink cover, real property name, generous white space, public guest URL and scannable QR. Grayscale must preserve hierarchy. Proposed interior: simple single-column text, readable embedded type, consistent margins, section headings and quiet page numbers. A table of contents is optional: omit for short output; if useful on longer books, generate from actual included headings/page positions (S06), never hand-maintained numbers. The threshold/design requires visual review, not a new product setting. No guaranteed fixed page count for variable-length content.

Snapshot/generation lifecycle should reuse SG-P01/SG-P21 request-version principles: capture property/load/content/workspace identity; obtain the latest accepted saved content through existing authorization flow; no token in library options or output. Disable duplicate actions, show accessible Preparing/Error/Retry feedback, and recheck identity after assets, QR and PDF work before initiating a download. Invalidate on property switch, recovery, newer accepted saved content or workspace close; no stale success/error must affect the next property. Async generation can lose a mobile download user gesture: retain a safe explicit Download-ready action if required by tested browsers, rather than popup/permission tricks. Local protected-preview credentials remain same-origin; do not touch SG-SHARE01 helpers.

### Dependency/font management proposal

After explicit approval only, pin the chosen pdfmake release and its documented browser build, record provenance/integrity and all required license/transitive notices. Prefer a reproducible local artifact/VFS produced through a documented maintenance step, with no new everyday frontend build workflow unless approved. Do not depend on mutable CDNs or third-party runtime fonts/scripts. The recommendation is not approval to vendor opaque assets or skip dependency review; an owner must choose/approve the exact version/distribution and update mechanism.

Measure compressed/uncompressed **dependency-closed** library+font transfers, parsing/generation time, peak memory and PDF size before accepting it. Don't compare one minified low-level file with an entire embedded-font bundle. Store fonts/code only as local immutable versioned assets loaded on export; host PDF assets must not become guest-page dependencies. A VFS font bundle avoids assuming the current Node adapter serves `.ttf` correctly; raw font loading instead requires an explicitly scoped MIME/asset check. PDF bytes can download in-browser without a new PDF MIME route/API. Existing CSP must not be relaxed globally; test the actual library under it, no eval/remote scripts requirement assumed.

## Privacy and security approval boundary

Guest-intended Wi-Fi network/password values may appear. Owner edit tokens, other authentication credentials, alarm secrets, keybox/entry/access codes and other non-guest information must not appear in PDF body, links, QR, filename, metadata, attachments, logs or cached artifacts. A code library is not a content classifier: the current free-text fields can contain forbidden secrets. A field allowlist alone cannot prove semantic privacy.

Before implementation, approve a concrete guest-content review policy: contextual export warning/review using existing saved data, clear separation of private reservation instructions from public guides, and handling of detected suspect content without silently rewriting or dropping benign text. Heuristic code-pattern checks cannot guarantee absence of secrets; never claim they do. For known/flagged private content, fail export pending host correction rather than printing it. This gate must not be used to add a separate PDF editor or redesign the default flow without approval. Full enforcement for arbitrary text remains a product/security decision under existing gates, not a claim solved here.

Treat text as plain text, not pdfmake instruction objects or HTML; escape native fallback HTML. Do not enable arbitrary auto-links, embedded scripts/files, external images/fonts or user-controlled fetch URLs. Retrieve only trusted same-origin canonical QR bytes with bounds; no owner-token forwarding. Keep names length-bounded/sanitized and URLs token-free. Revoke temporary Blobs; inspect logs/network with synthetic sentinels only. Changing the download origin requires the existing stable-public-URL warning policy. No permanent domain or production safety guarantee is invented.

## Bounded implementation plan after owner approval

1. **Approve technology and unresolved policies:** exact dependency/distribution/font/license/update choices, browser support, payload/performance budget, script/glyph limitations, secret-content handling and minimal-content/contents policy. Keep D-013 open until explicit selection; no installation before approval.
2. **Prove the approved browser path on synthetic fixtures:** A4/A5 real PDF bytes; embedded Greek/required fonts; multipage long text; canonical SVG conversion; downloads on representative supported browsers/devices; actual asset/memory/CPU measurements.
