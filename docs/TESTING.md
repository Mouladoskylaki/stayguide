# Testing strategy

## Baseline
`npm test` — Node test suite. Record actual result per task, never assume. `npm start` — local preview on http://127.0.0.1:8787. Localhost QR cannot be opened from a separate phone; use a reachable HTTPS staging URL only after authorization.

## Every task
- Run tests and report count; `git diff --check`; test changed routes and edge cases.
- UI changes: browser at ~390px and ~1440px, check horizontal overflow, contrast, keyboard focus and content with JS disabled.
- Security changes: unauthenticated edits denied; XSS text escaped; public page noindex; no edit tokens in public responses.
- Print: A4/A5 page breaks, QR scan, SVG/PNG exports, no cut-off content.
- Translation: fallback, stale-source invalidation, no repeated translation on view, cost ceilings.

## Release gates
No launch until account/trial security, upload controls, payments/webhooks, privacy, monitoring and restore testing pass. Distinguish automated tests, manual checks, and untested claims.

## SG-P31-W4B-A — source metadata and explicit declaration

Owner-authenticated `GET /api/guides/{id}/translation-sources/{section}` returns only `{section, sourceLanguage, sourceVersion, declared}`. Undeclared language remains null; legacy stored tags outside the milestone remain unchanged on read. This operation neither instantiates the OpenAI provider nor reads provider/credential bindings, generates, claims or reserves spending.

`PATCH` on the same URL requires application/json and exactly `{sourceLanguage, expectedSourceVersion}`, bounded to 4,096 raw body bytes. Declaration accepts only el-GR/en-GB/de-DE/fr-FR/it-IT/es-ES and a positive safe integer version. No clear/null declaration, inference, bulk update or host control is added. Authentication precedes section validation and body parsing. Responses: 200 metadata; 400 invalid body/tag/version/content type; 401 unauthorized; 404 unknown guide/section or absent metadata; 409 with source_version_conflict for stale expectations; sanitized 500 source_metadata_unavailable for unexpected storage/result failures. Responses retain no-store/nosniff behavior.

The UPDATE matches guide/section/source_version atomically, sets the chosen language and adds zero or one to the version using a CASE expression against the old language. A RETURNING row with applied=1 and the resulting metadata is required; trigger-inclusive meta.changes is not used. Same-language no-ops still pass through this version-checked SQL, so stale same-language calls cannot succeed. Version-changing competitors have one winner; valid no-ops do not consume a version. Existing invalidation triggers only stale the changed section when the version actually advances. A positive safe-integer ceiling prevents increment overflow. Returned metadata represents the operation's atomic statement, not a later read that could accidentally report another writer's result. A follow-up read after zero returned rows only distinguishes missing metadata/conflict/storage failure; it does not authorize or retry a write.

## SG-P31-W4B-B — version-aware generation and permanent attempt fence

Owner-authenticated `POST /api/guides/{id}/translations` requires application/json, at most 4,096 body bytes and exactly `{section, sourceLanguage, targetLanguage, expectedSourceVersion}`. The version must be a positive safe integer. Both tags must belong to el-GR/en-GB/de-DE/fr-FR/it-IT/es-ES. Wider legacy storage/read support is preserved. A section must already have an explicit source declaration from Stage A. Generation never calls the source setter, declares a language, increments a source version or invalidates translations. Legacy three-field requests are rejected; clients must read metadata and explicitly declare source language separately. Never infer it from host UI language.

The service requires explicit language/version expectations. It validates before cache reuse, verifies that independent cache/source reads still represent that expectation, and binds the unchanged version to the atomic claim SQL. It never refreshes a caller expectation. Current generated/manual cache results return before claims, even with live execution disabled. Source changes during work cannot pass conditional publication; post-publication reads also reject a replaced version. There remains no generation from guest views.

The claim's `INSERT ... SELECT ... WHERE ... RETURNING 1 AS applied` now includes `NOT EXISTS` over translation_attempts matching guide, section, source language, target language, source version, model, prompt version and provider mode. This predicate is inside the atomic SQL operation, in addition to source/version, budget, request, rate and translation-row predicates. Any existing attempt blocks a new claim regardless of status or lease. Expiry, provider failure and uncertain execution are terminal for this identity. No attempts are deleted, reset or replaced and no reservations are refunded. A new saved source version is a distinct identity, still subject to existing limits. The JSON adapter performs the equivalent identity check within its existing locked write. Direct RETURNING verification remains authoritative; trigger-inclusive meta.changes is not a direct-row count.

Sanitized responses distinguish invalid requests (400), ownership failure (401), missing guide/source (404), declaration/language/version conflicts and pending/terminal attempts (409), input limits and aggregate fixture budget/request/rate rejection (409), default-disabled live provider (503), provider/validation/storage failure (502), and timeout/uncertain execution (504). Categories include source_language_required, source_language_changed, source_version_changed, attempt_pending, attempt_terminal, input_limit, busy_or_limit, live_disabled, translation_unavailable and translation_timeout_uncertain. Failure responses do not expose raw errors or private content; saved-only views retain original-language fallback. Reservations describe allocated budget, not confirmed provider billing. Model/processing, 1,200 source code points, 800/800 tokens, $0.00066 reservation, publication leases and zero retries remain unchanged. Mock payload byte checks remain conservative and are not real token counts.

Historical harness compatibility: only its `execution === 'offline-mock'` caller adds a separate Stage A declaration and expected version to synthetic POSTs. The consumed live branch, exclusive guard, credential reader, fixed H08 provider payload and historical evidence/guards are unchanged. Its obsolete live POST is intentionally not made compatible or reauthorized. Do not remove guards or execute --live. Existing offline foundation/integration/concurrency callers now explicitly obtain and submit saved expectations; there is no legacy HTTP bypass.

### Availability and request contract

Authenticated `GET /api/guides/{id}/translation-capabilities` accepts exactly four query fields: `section`, `sourceLanguage`, `targetLanguage`, `expectedSourceVersion` (canonical positive integer). It returns `{generationAvailable, testOnly, state, sourceVersion}` without source text, credentials or private configuration. Existing guide ownership checks precede capability inspection. No adapter is constructed and no live flag or API key is read. Default state is unavailable, including when the capability response is unreadable/malformed. Only trusted server bindings supplied by isolated tests (`TRANSLATION_OFFLINE_TEST === true` plus an explicitly enabled injected OpenAI-mode fake provider) expose the action; browser flags/query/header values cannot enable it. No tracked runtime configuration enables these bindings. This is not production authorization or a general provider-health check.

Under the explicit test binding, capability reads existing sources, current cache and durable attempts without writes: missing/stale declaration, same language, empty/over-1,200-code-point source and pending/terminal attempts block the action. Capability is advisory, not a replacement for the authoritative POST claim, budget and version checks. It does not reserve spending or promise future budget availability.

The host requires a clean saved section and declared source, different supported target and explicit native confirmation before sending exactly `{section, sourceLanguage, targetLanguage, expectedSourceVersion}` to the existing owner POST /translations. It never implicitly declares a source, truncates text, bulk generates, refreshes stale expectations for resubmission, or dispatches on locale/target/status changes. It requires a valid POST result and subsequent authenticated saved GET/source-version verification before announcing success. Original text is never replaced. Synthetic generation is clearly labelled as offline test output.

A conservative per-session identity marker is set before dispatch; repeated clicks/failures cannot redispatch. Durable server attempt history remains authoritative across reloads. Pending, failed, expired, uncertain and terminal identities have no Retry action. Explicit status refresh performs reads only and retains a still-valid target while clearing/revalidating the old preview. Editor/property/request serials fence late UI updates; source edits fence database publication. Sanitized, localized states cover unavailable, draft/empty/long source, changed version, saved result, in-progress, pending, terminal, budget/rate, provider failure and uncertain network/timeout outcomes. Live regions and native keyboard controls are retained.

### Owner API and storage contract

`PATCH /api/guides/{id}/translations` authenticates the existing guide owner **before reading the body**. Content-Type must be application/json. Exactly four top-level keys are accepted:

```json
{
  "section": "arrival",
  "targetLanguage": "de-DE",
  "fields": {"checkin": "Ankunft 15:00.", "checkout": "Abreise 11:00."},
  "expected": {
    "sourceVersion": 2,
    "translationId": "<exact identity returned by the saved view>",
    "translatedText": "<exact serialized snapshot returned by the saved view>"
  }
}
```

`expected` has exactly those three keys. Its snapshot is the **old** saved serialized text, never the proposed correction or a silently refreshed expectation. Nine eligible sections and the six milestone languages only (both current declared source and requested target). Fields must exactly match the section allowlist; property names, Wi-Fi fields and arbitrary extra keys are rejected. Strings are bounded to the existing 3,200 UTF-8 bytes per translated field. The endpoint caps the streamed body at **98,304 bytes (96 KiB)** and the serialized previous snapshot at 40,000 bytes. This accounts for two fields plus JSON escaping of the exact previous snapshot; the old 4 KiB generation/source request limit remains unchanged. No text is truncated.

The route uses a storage-only OpenAI-mode service boundary, with generation unavailable. It never resolves an injected generation provider, live flag or credential callback. Existing `service.correct()` validates safe text, protected strings, empty-field parity, current source version, exact cached identity and previous text. Existing `store.correct()` binds these expectations to atomic SQL RETURNING, including current source/version predicates. Mock rows, originals, missing/stale/replaced translations and outdated/competing snapshots cannot be corrected or created through this route. Original guide data, source metadata, generation attempts and spending reservations are untouched.

Success is `{status: "corrected"}` (HTTP 200); the UI must read back and verify the saved result. Shape/type/size violations return sanitized HTTP 400; unavailable guide/unauthorized owner use existing 404/401. A failed semantic validation/CAS or sanitized correction storage failure returns HTTP 409 `correction_conflict`. This deliberately does not reveal whether the underlying failure was a race, invalid protected content or a storage failure. No raw database/provider details are returned, and no retries are performed.
